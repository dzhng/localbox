# Sandbox images: choices ledger

Decisions made where the spec was silent, appended per pass. Verdicts: **sound**,
**provisional** (revisit at the named slice), **user** (needs the user's call;
the recorded provisional call stands meanwhile).

- **15 — GRUB, not systemd-boot, with a fixed config reading the kernel symlinks.**
  Sound. GRUB reads the kernel from the ext4 root, so a kernel install only has to
  repoint `/boot/vmlinuz` (which Ubuntu's kernel packages already do); systemd-boot
  would need every kernel copied onto the EFI partition by kernel-install hooks.
  Alternative: systemd-boot with kernel-install.
- **15 — `update-grub` is replaced by `true` in the image.** Sound. grub-mkconfig
  would overwrite the fixed config with device-specific entries; nothing in the
  image needs it. Alternative: let it run and depend on its device detection in a VM.
- **15 — the kernel-upgrade test installs the HWE kernel.** Sound. The image already
  has the newest GA kernel, so "a newer kernel" is only reliably available as the
  HWE series; it proves the same thing (a different version boots). Alternative:
  pin the image to an older GA kernel.
- **15 — `AppleVirtualizationBackend` takes an optional configuration closure.**
  Provisional — slice 23 replaces it with `VMSpec`. It let vmlab boot an EFI
  configuration through the real backend (channel, save, restore) without copying
  the backend. Alternative: a parallel lab-only backend.
- **21 — every `image.*` op has executor `account` and names no sandbox.** Convex owns the image record (single-owner table), so the CLI always sends image ops to the agent API; `image.create`'s source sandbox travels as input `from`, because the op is about an image, not about acting on that sandbox. Alternative: `host` executor for create/copy/wait, which would let the CLI try the local daemon first and split ownership of the record.
- **21 — `image.delete` input is `{ image, confirm? }`; `--machine` stays on the envelope.** The slice's input column lists `machine?` while its note says `--machine` is the routing selector, not input; the CLI never puts a control flag into input anyway. Alternative: a `machine` input field, which would make the one op that routes by machine differ from every other.
- **21 — "exactly one of `from`/`macos`" lives in `validateInput` (contract), not a JSON Schema `oneOf`; `macos` only accepts `true`.** A top-level `oneOf` in a tool input schema is refused by common model tool APIs that read the MCP tool list. `validateRequest` and the relay both call `validateInput`. Alternative: two ops (`image.capture`, `image.build`), which renames commands the user chose (Q10).
- **21 — `hostOperationIds` = host executor ∪ account ops routed to machines or holders ∪ the named `sandbox.list`.** `sandbox.list` is the one account read the daemon also answers (a signed-out CLI lists local sandboxes), so it is listed by name rather than by a prefix. Alternative: a fourth per-op flag, which would restate what routing already says for every other op.
- **21 — HostDaemon answers the four relayed image ops `unsupported` until the daemon slices build them.** Regenerating `GeneratedOperations.swift` adds them to `HostOperation`, and `SandboxHost`'s exhaustive switch must name them to compile; that is the only Swift change. Alternative: keep image ops out of the generated enum until slice 26, which needs a special case in `hostOperationIds` and contradicts slice 21's "See it".
- **21 — `tests/contract-executor.test.ts` becomes `tests/catalog-routing.test.ts`.** The new literal routing table covers the old executor and scope lists, so keeping both would state each op's route twice; probe 09 now runs the renamed file. Alternative: two tests asserting overlapping tables.
- **21 — `ImageOperationState.error` is `{ code, message, next_step }`.** The failed state must carry the reason and the next step (Q5, output standard); `code` reuses the contract's error codes so the CLI renders it like any other error. Alternative: free text only.
- **22 — `images.sizeBytes` is optional: absent until a holder reports the image `ready`, and `setHolder` carries `sizeBytes` with that report.** A capture or build doesn't know its size at reserve time, and 0 would read as a real size in `image list`. Alternative: a separate `setSize` function, a second write path for one field.
- **22 — `reserve` takes the building machine and writes its `building` holder row in the same mutation, deduped on `createMutationId`.** A reserved image with no holder would list as orphaned until the connector's first report. Alternative: reserve the row only and let slice 26's connector report create the holder.
- **22 — `setHolder` is machine-only (the caller's own holding); `dropHolder` is an account call naming the machine.** Holder state is what a Mac reports about itself (connector), while `image delete --machine` runs as the agent or CLI caller (slice 30). Alternative: both machine-only, which would make the relay call as a machine it isn't.
- **22 — the synthesized `linux` row has `image_id: "linux"`, `source: { kind: "release" }`, `size_bytes: null`, `created_at: null`.** It isn't a row (P1), so it has no id, size or creation time; `release` says where it comes from without widening the stored `source` union. Alternative: a fake id and size per machine.
- **22 — built-in names refuse with `invalid_input`, taken names with `name_conflict`; `setDefault linux` clears `defaultImageId`.** Absent already means `linux`, so storing it would be a second spelling of the same state. Alternative: store `"linux"` explicitly.
- **22 — generated image names reuse `sandboxName()` (adjective-animal).** The map's samples (`brave-walrus`) use that shape; a second generator would be the same lists. Alternative: rename it to a neutral name in `packages/names`.
- **22 — the `images`, `imageHolders` validators live in `schema.ts`.** `images.ts` imports `lib/relay.ts`, which imports `schema.ts`, so defining them in `images.ts` would make the schema import a function module. Alternative: a separate validators file.
- **36 — the per-machine image fields (`holds`, `heldAt`, `freeDiskBytes`, `macOSVersion`, `macVMsRunning`) are optional, each with a cautious reading when absent.** No disk reported means no copy goes there (`disk_full` says it wasn't reported); no macOS version means no macOS image goes there. Capacity gains disk and version only in slice 24, and the create route has no image yet. Alternative: required fields that the relay fills with made-up values until then.
- **36 — auto/remote copies to a non-holder only when that machine has room; when no holder has room and no roomy machine can take a copy, a holder makes room as today.** Copying gigabytes to a machine that must then also make room is worse than making room where the image already is. Alternative: the slice's literal rule (roomiest non-holder with disk, whether or not it fits).
- **36 — a Mac already running `MAC_VM_LIMIT` (2) macOS guests counts as having no room for a macOS image.** Auto then prefers a Mac with a free slot; a named or own Mac is still used, and its admission sleeps a guest or answers `machine_full` (E11). Alternative: ignore the count in placement and leave it all to admission.
- **36 — a copy comes only from an online holder (most recent `heldAt`, then name).** A copy needs the source to answer. Offline holders only give `machine_offline` naming them; no holder at all gives `image_not_found`. Alternative: plan from an offline holder and let the copy wait for it.
- **36 — `BUILT_IN_IMAGE = "linux"` lives in the contract, shared by `images.ts` and `place()`; the create route places that image until slice 29 resolves `image`.** One spelling of the built-in name across Convex, placement and the relay. Alternative: the literal repeated in each package.
- **36 — `minMacOS` and `macOSVersion` are dotted strings compared numerically (`atLeast`).** That's how macOS reports versions, and "27.10" must beat "27.9". Alternative: store major/minor as numbers.
- **26 — The record type is `HostOperationRecord`, not `ImageOperationState`.** The store is kind-agnostic (the slice's firewall: no image logic here), and build, copy, capture and create-with-copy all land in it. Alternative: an image-named type, which would put image vocabulary into a generic owner.
- **26 — The record carries a `checkpoint` (any JSON) beside `progress`, seeded by `begin` and replaced by every `report`.** A resumer needs the kind's own resume point (a phase, a chunk bitmap) and any input the work needs, even if the daemon dies before the work's first report; `progress` (phase, completed, total) is only what callers are shown. Alternative: fold the resume point into `progress`, which would show callers a bitmap, or persist the request input separately.
- **26 — `begin(kind:key:subject:checkpoint:work:)` refuses a kind with no registered resumer.** Every journaled record must be continuable after a restart, so a kind that can start but not resume is a bug caught at the first call. Alternative: allow it and fail the record at the next start.
- **26 — An unfinished record whose kind no longer registers a resumer fails with `unsupported` at start.** No compat path for kinds a build dropped; a waiter learns it will never finish instead of polling forever. Alternative: leave it `running`, or delete it.
- **26 — `wait` returns when the work finishes or after the timeout, not on each progress change; `timeoutMs` is clamped to 0…120 000.** The caller's `{continue}` loop re-polls anyway and each answer carries the current progress; streaming phases sooner is slice 34's call if it needs it. Clamping (rather than refusing) keeps an over-long client request a normal bounded answer. Alternative: also return on a phase change, or refuse a timeout above 120 s with `invalid_input`.
- **26 — Journal timestamps are integer milliseconds since 1970 (`started_at`, `updated_at`).** ISO 8601 drops sub-second precision, so a record read back after a restart differed from the one a replay got before it; whole milliseconds round-trip exactly and match the relay's `deadline_at`. Alternative: fractional ISO 8601 with dates truncated in memory.
- **26 — Journals are never pruned in this pass.** A finished record must outlive the relay's replay window to answer a late replay, and nothing yet says how long that is. Alternative: prune finished records after a fixed age at start (left to the slice that first produces many operations).
- **26 — The daemon takes the directory as `LOCALBOX_OPERATIONS`, materialized by `install-release.sh`/`rollback-release.sh` and the proof stacks like `LOCALBOX_SANDBOXES`.** Paths reach the daemon explicitly, never derived from another path; the installer is what makes them follow `LOCALBOX_MACHINE_ROOT`. `stack up` wipes it with the sandboxes, since its keys belong to the wiped Convex account. Alternative: derive it from the sandboxes directory's parent.
- **26 — The daemon resumes operations after `host.recover()`.** A resumed capture or create-with-copy may act on a sandbox, which must be back first. Alternative: resume before the socket opens.

- **31 — The agent is packaged with `bun build --compile`, pinned to Bun 1.4.4.** One command cross-compiles both targets from a Mac (the linux runtime comes from Bun's cache), the output is byte-identical for the same sources, Bun version and output name, and both binaries run with no runtime installed (linux checked on bare `ubuntu:24.04`). The build refuses any other Bun version, because a different compiler changes every digest. Alternative: a Node single executable application, which keeps Node as the runtime but needs a bundler, `postject`, a pinned linux Node download and separate darwin signing.
- **31 — Bun is a required tool on PATH, not an npm dependency.** npm 11 doesn't run install scripts without approval, and the `bun` package needs its postinstall to place the native binary. `tests/agent-binary.test.ts` skips, saying why, when Bun 1.4.4 is missing (the release-checks CI job has neither Bun nor Docker). Alternative: add `oven-sh/setup-bun` to CI.
- **31 — Standalone executables are built with `--no-compile-autoload-dotenv --no-compile-autoload-bunfig`.** Otherwise the agent loads `.env` and `bunfig.toml` from its working directory (the repo, for the process fixture), and those variables reach every command it runs. Alternative: none that keeps the environment clean.
- **31 — `agent-version.json` is `{ version: "<release>+<12 hex>", sha256: { linux, darwin } }`.** The 12 hex characters are the start of sha256 over `linux:<sha>\ndarwin:<sha>\n`, so a change to either binary is a new version; semver build metadata keeps the release version readable. Digests are bare hex, since the field name already says sha256. Alternative: a separate version per OS.
- **31 — The darwin binary keeps Bun's ad-hoc linker signature; the release doesn't re-sign it.** `codesign --deep` on the app seals `Contents/Resources/guest-agent/` as resources without rewriting those bytes (checked), so the digests in `agent-version.json` stay true. The binary runs inside a macOS guest, not on the host, and slice 33 decides what that guest needs. Alternative: sign it with the release identity before writing `agent-version.json`, inside the build script.
- **31 — The image build builds the agent before hashing its inputs, and hashes only the binary the Dockerfile copies.** Before, `dist/` was hashed before `npm run build`, so a cache hit could be a stale agent. `.dockerignore` now keeps all of `dist/` except `dist/guest-agent` out of the build context. Alternative: keep hashing all of `dist/`.
- **31 — `tests/agent-binary.test.ts` drives the binary over stdin/stdout itself, the way the process fixture does, rather than through the Swift fixture.** The fixture's guest command is Swift (`localbox-hostd/main.swift`), outside this slice. On a Mac the linux binary runs in `docker run --platform linux/arm64 ubuntu:24.04` and the test asserts the container has no Node; the darwin binary runs natively. Alternative: point `ProcessFixtureConfiguration` at the binary (later, with Swift).
- **23 — `SandboxConfigurationBuilder.build` validates; tests inspect the unvalidated `configuration(for:)`.** `validate()` refuses in any process without the virtualization entitlement, and `swift test` runs an unsigned xctest. `VMSpecTests` checks the translation (EFI boot loader, variable store, no kernel), and probe 23 (tier v) proves validation and boot through the signed vmlab. Alternative: sign the xctest bundle in `swift test`, which SwiftPM gives no hook for.
- **23 — the record stores the image id, OS and macOS hardware model, not a boot store path.** The boot store's file name follows from the OS (`SandboxDirectory.bootStore(for:)`: `efi-vars` or `aux.img`), so a stored path would be a second spelling; the hardware model is stored because a restore needs it and the image may be deleted. Alternative: a `boot_store` path field in `sandbox.json`.
- **23 — `os` is set by `provision`, not by `SandboxRecord.init`.** Only the image knows its OS, and the factory is what reads the image (slice 24); `SandboxHost` names only the image id. Alternative: `SandboxHost` reads the manifest first, which would put image file I/O in `SandboxHost`.
- **23 — `VMSpec.devices` is computed from `GuestPlatform.devices(for: os)`, and the translator iterates it.** One list per OS decides what is attached, so "macOS has no entropy device" is a pure assertion. Alternative: device flags on `VMSpec`, which could disagree with the platform.
- **23 — macOS display is 1440x900 at 80 ppi, no window.** Matches the Linux image's desktop size, so desktop operations see one size on both. Alternative: Tart's 1920x1200; slice 35 may revisit with real screenshots.
- **23 — vmlab's `--kernel-args` and the `kernel_command_line` restore sweep are gone.** EFI has no host-side command line, and the direct path is a seam deleted in 24. Alternative: keep them for the seam's lifetime.
- **23 — `AppleVirtualizationBackend(spec:sandboxID:name:)` replaces the lab-only `ConfigurationMaker`.** vmlab builds its experiments as `VMSpec`s (changing the record for the restore sweep), so every lab boot goes through the production translator. Alternative: keep a closure for labs.
- **23 — probe `23-vmspec-bootstore.ts`: tier s runs `VMSpecTests`, tier v boots and hibernates the slice 15 EFI disk through vmlab `--efi`.** The slice names both gates; vmlab is the only real-VM harness before 24 provisions EFI sandboxes in the daemon. Alternative: reuse probe 15, whose evidence file is the spike's record.
