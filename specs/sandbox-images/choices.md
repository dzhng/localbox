# Sandbox images: choices ledger

Decisions made where the spec was silent, appended per pass. Verdicts: **sound**,
**provisional** (revisit at the named slice), **user** (needs the user's call;
the recorded provisional call stands meanwhile).

- **15 — GRUB, not systemd-boot, with a fixed config reading the kernel symlinks.**
  Sound. GRUB reads the kernel from the ext4 root, so a kernel install only has to
  repoint `/boot/vmlinuz` (which Ubuntu's kernel packages already do); systemd-boot
  would need every kernel copied onto the EFI partition by kernel-install hooks.
  Alternative: systemd-boot with kernel-install.
- **15 — `update-grub` is replaced by `true` in the image.** Sound. grub-mkconfig
  would overwrite the fixed config with device-specific entries; nothing in the
  image needs it. Alternative: let it run and depend on its device detection in a VM.
- **15 — the kernel-upgrade test installs the HWE kernel.** Sound. The image already
  has the newest GA kernel, so "a newer kernel" is only reliably available as the
  HWE series; it proves the same thing (a different version boots). Alternative:
  pin the image to an older GA kernel.
- **15 — `AppleVirtualizationBackend` takes an optional configuration closure.**
  Provisional — slice 23 replaces it with `VMSpec`. It let vmlab boot an EFI
  configuration through the real backend (channel, save, restore) without copying
  the backend. Alternative: a parallel lab-only backend.
- **21 — every `image.*` op has executor `account` and names no sandbox.** Convex owns the image record (single-owner table), so the CLI always sends image ops to the agent API; `image.create`'s source sandbox travels as input `from`, because the op is about an image, not about acting on that sandbox. Alternative: `host` executor for create/copy/wait, which would let the CLI try the local daemon first and split ownership of the record.
- **21 — `image.delete` input is `{ image, confirm? }`; `--machine` stays on the envelope.** The slice's input column lists `machine?` while its note says `--machine` is the routing selector, not input; the CLI never puts a control flag into input anyway. Alternative: a `machine` input field, which would make the one op that routes by machine differ from every other.
- **21 — "exactly one of `from`/`macos`" lives in `validateInput` (contract), not a JSON Schema `oneOf`; `macos` only accepts `true`.** A top-level `oneOf` in a tool input schema is refused by common model tool APIs that read the MCP tool list. `validateRequest` and the relay both call `validateInput`. Alternative: two ops (`image.capture`, `image.build`), which renames commands the user chose (Q10).
- **21 — `hostOperationIds` = host executor ∪ account ops routed to machines or holders ∪ the named `sandbox.list`.** `sandbox.list` is the one account read the daemon also answers (a signed-out CLI lists local sandboxes), so it is listed by name rather than by a prefix. Alternative: a fourth per-op flag, which would restate what routing already says for every other op.
- **21 — HostDaemon answers the four relayed image ops `unsupported` until the daemon slices build them.** Regenerating `GeneratedOperations.swift` adds them to `HostOperation`, and `SandboxHost`'s exhaustive switch must name them to compile; that is the only Swift change. Alternative: keep image ops out of the generated enum until slice 26, which needs a special case in `hostOperationIds` and contradicts slice 21's "See it".
- **21 — `tests/contract-executor.test.ts` becomes `tests/catalog-routing.test.ts`.** The new literal routing table covers the old executor and scope lists, so keeping both would state each op's route twice; probe 09 now runs the renamed file. Alternative: two tests asserting overlapping tables.
- **21 — `ImageOperationState.error` is `{ code, message, next_step }`.** The failed state must carry the reason and the next step (Q5, output standard); `code` reuses the contract's error codes so the CLI renders it like any other error. Alternative: free text only.
- **22 — `images.sizeBytes` is optional: absent until a holder reports the image `ready`, and `setHolder` carries `sizeBytes` with that report.** A capture or build doesn't know its size at reserve time, and 0 would read as a real size in `image list`. Alternative: a separate `setSize` function, a second write path for one field.
- **22 — `reserve` takes the building machine and writes its `building` holder row in the same mutation, deduped on `createMutationId`.** A reserved image with no holder would list as orphaned until the connector's first report. Alternative: reserve the row only and let slice 26's connector report create the holder.
- **22 — `setHolder` is machine-only (the caller's own holding); `dropHolder` is an account call naming the machine.** Holder state is what a Mac reports about itself (connector), while `image delete --machine` runs as the agent or CLI caller (slice 30). Alternative: both machine-only, which would make the relay call as a machine it isn't.
- **22 — the synthesized `linux` row has `image_id: "linux"`, `source: { kind: "release" }`, `size_bytes: null`, `created_at: null`.** It isn't a row (P1), so it has no id, size or creation time; `release` says where it comes from without widening the stored `source` union. Alternative: a fake id and size per machine.
- **22 — built-in names refuse with `invalid_input`, taken names with `name_conflict`; `setDefault linux` clears `defaultImageId`.** Absent already means `linux`, so storing it would be a second spelling of the same state. Alternative: store `"linux"` explicitly.
- **22 — generated image names reuse `sandboxName()` (adjective-animal).** The map's samples (`brave-walrus`) use that shape; a second generator would be the same lists. Alternative: rename it to a neutral name in `packages/names`.
- **22 — the `images`, `imageHolders` validators live in `schema.ts`.** `images.ts` imports `lib/relay.ts`, which imports `schema.ts`, so defining them in `images.ts` would make the schema import a function module. Alternative: a separate validators file.
- **36 — the per-machine image fields (`holds`, `heldAt`, `freeDiskBytes`, `macOSVersion`, `macVMsRunning`) are optional, each with a cautious reading when absent.** No disk reported means no copy goes there (`disk_full` says it wasn't reported); no macOS version means no macOS image goes there. Capacity gains disk and version only in slice 24, and the create route has no image yet. Alternative: required fields that the relay fills with made-up values until then.
- **36 — auto/remote copies to a non-holder only when that machine has room; when no holder has room and no roomy machine can take a copy, a holder makes room as today.** Copying gigabytes to a machine that must then also make room is worse than making room where the image already is. Alternative: the slice's literal rule (roomiest non-holder with disk, whether or not it fits).
- **36 — a Mac already running `MAC_VM_LIMIT` (2) macOS guests counts as having no room for a macOS image.** Auto then prefers a Mac with a free slot; a named or own Mac is still used, and its admission sleeps a guest or answers `machine_full` (E11). Alternative: ignore the count in placement and leave it all to admission.
- **36 — a copy comes only from an online holder (most recent `heldAt`, then name).** A copy needs the source to answer. Offline holders only give `machine_offline` naming them; no holder at all gives `image_not_found`. Alternative: plan from an offline holder and let the copy wait for it.
- **36 — `BUILT_IN_IMAGE = "linux"` lives in the contract, shared by `images.ts` and `place()`; the create route places that image until slice 29 resolves `image`.** One spelling of the built-in name across Convex, placement and the relay. Alternative: the literal repeated in each package.
- **36 — `minMacOS` and `macOSVersion` are dotted strings compared numerically (`atLeast`).** That's how macOS reports versions, and "27.10" must beat "27.9". Alternative: store major/minor as numbers.
- **26 — The record type is `HostOperationRecord`, not `ImageOperationState`.** The store is kind-agnostic (the slice's firewall: no image logic here), and build, copy, capture and create-with-copy all land in it. Alternative: an image-named type, which would put image vocabulary into a generic owner.
- **26 — The record carries a `checkpoint` (any JSON) beside `progress`, seeded by `begin` and replaced by every `report`.** A resumer needs the kind's own resume point (a phase, a chunk bitmap) and any input the work needs, even if the daemon dies before the work's first report; `progress` (phase, completed, total) is only what callers are shown. Alternative: fold the resume point into `progress`, which would show callers a bitmap, or persist the request input separately.
- **26 — `begin(kind:key:subject:checkpoint:work:)` refuses a kind with no registered resumer.** Every journaled record must be continuable after a restart, so a kind that can start but not resume is a bug caught at the first call. Alternative: allow it and fail the record at the next start.
- **26 — An unfinished record whose kind no longer registers a resumer fails with `unsupported` at start.** No compat path for kinds a build dropped; a waiter learns it will never finish instead of polling forever. Alternative: leave it `running`, or delete it.
- **26 — `wait` returns when the work finishes or after the timeout, not on each progress change; `timeoutMs` is clamped to 0…120 000.** The caller's `{continue}` loop re-polls anyway and each answer carries the current progress; streaming phases sooner is slice 34's call if it needs it. Clamping (rather than refusing) keeps an over-long client request a normal bounded answer. Alternative: also return on a phase change, or refuse a timeout above 120 s with `invalid_input`.
- **26 — Journal timestamps are integer milliseconds since 1970 (`started_at`, `updated_at`).** ISO 8601 drops sub-second precision, so a record read back after a restart differed from the one a replay got before it; whole milliseconds round-trip exactly and match the relay's `deadline_at`. Alternative: fractional ISO 8601 with dates truncated in memory.
- **26 — Journals are never pruned in this pass.** A finished record must outlive the relay's replay window to answer a late replay, and nothing yet says how long that is. Alternative: prune finished records after a fixed age at start (left to the slice that first produces many operations).
- **26 — The daemon takes the directory as `LOCALBOX_OPERATIONS`, materialized by `install-release.sh`/`rollback-release.sh` and the proof stacks like `LOCALBOX_SANDBOXES`.** Paths reach the daemon explicitly, never derived from another path; the installer is what makes them follow `LOCALBOX_MACHINE_ROOT`. `stack up` wipes it with the sandboxes, since its keys belong to the wiped Convex account. Alternative: derive it from the sandboxes directory's parent.
- **26 — The daemon resumes operations after `host.recover()`.** A resumed capture or create-with-copy may act on a sandbox, which must be back first. Alternative: resume before the socket opens.
- **26 — A host operation's `subject` is the image it produces on that Mac, and the daemon's `image.wait` follows the image's most recently started record.** `image.wait`'s input is the image, not an operation key, and a retried copy or build starts a new record for the same image; the connector also reports each outcome as that image's holder state. Kinds in 28, 34, 38 and 39 must begin with `subject` = the image id. Alternative: an `operation_id` input on `image.wait`, which the public contract would have to carry for every caller.
- **26 — Each `begin` takes a `started_at` later than any before it in that journal (at least now, else the last plus 1 ms).** "The image's most recent operation" must never tie: two begins in the same millisecond made `image.wait` follow the older record. Alternative: a separate sequence number in every record.
- **26 — The daemon answers `image.wait` with its operation record; the relay turns it into `ImageOperationState`, on the first call and on every continuation.** Convex owns the image's name and OS and whether a holder is `building` or `copying`; the daemon owns progress. Composing in the relay keeps the store kind-agnostic, and doing it on the continuation path too means a wait that outlives one HTTP call reads the same. Alternative: the daemon composes the state, which needs the name (renamable) and OS copied into every record.
- **26 — `ImageHost` (new actor) answers image operations and the connector's `host.operations`; `SandboxHost` only routes them there.** The single-owner table says `SandboxHost` never does image work; routing in `SandboxHost.request` keeps one socket entry point. Alternative: a router in front of `SandboxHost` inside `AuthenticatedLocalIPC`, which changes every IPC constructor.
- **26 — Outcomes reach Convex through an outbox: the record's `reported_at`, set when the connector's next `host.operations` poll lists the key as reported.** A finished operation is handed over until its report lands, across restarts of the daemon or the connector, and never again after, so a holder dropped by `image delete --machine` is not resurrected by a re-report. An image the account deleted meanwhile (`image_not_found`) counts as reported. Alternative: report every finished record on each connector start, which re-creates dropped holder rows.
- **26 — `imageHolders` gains `error { code, message, nextStep }`, set only while `failed` (`setHolder` refuses either half alone); `images:get` resolves one image as `list` shows it, with `operation_id` and `error` per holder.** `image.wait` answers from the catalog when no Mac is building or copying, and a failed state must carry the reason and next step (Q5). `get` keeps name resolution (`linux`, `macos`) in `images.ts`. Alternative: keep failures only in the daemon's journal, so a wait on a failed image would have to reach an offline Mac.
- **26 — `HostOperationFailure` carries an optional `next_step`; the relay fills a generic one (delete and recreate) when a kind gave none.** The kind knows what to try next; store-level failures (`unsupported`, `internal`) don't. Alternative: the relay maps codes to next steps, a second owner of failure wording.
- **26 — Progress `completed`/`total` map to `done_bytes`/`total_bytes`; image kinds report bytes there, and a phase without counts reads 0/0.** The contract names bytes; the store stays generic. Alternative: widen `ImageOperationState.progress` to optional counts.
- **26 — The daemon's `image.wait` waits `min(timeout_ms, deadline_ms − 1 s)`, as `job.wait` does, and the CLI gives any command with `--timeout-ms` a deadline of `timeout_ms + 5 s` (at most 120 s) unless `--deadline-ms` is given.** The default 30 s deadline would cut a 120 s wait short; this applies to `job wait` too. Alternative: special-case `image wait` in the CLI.
- **26 — Dev daemons (`LOCALBOX_DEV=1`) register the fixture kind `sleep_steps` (`FixtureOperations.swift`) and answer `host.begin_operation`, as `host.simulate_power` is dev-only.** No catalog operation begins a kind until slice 28, but probe 26 needs a real daemon running, restarting and reporting one. Alternative: register the fixture only in the test target, leaving tier `l` nothing to run.
- **26 — `stack.ts restart --machines b` SIGKILLs a daemon and starts it on the state it left; `up` still starts from empty.** Probe 26 kills the daemon mid-operation; `up` wipes the operations journal with the account. Alternative: a probe-local daemon launcher duplicating the stack's environment.
- **30 — The daemon reaches image files only through `ImageFiles` (`list() -> [HeldImage]`, `markListed(_:by:)`, `remove(_:) -> Bool`, in `ImageHost.swift`), backed by `StoredImageFiles` over slice 24's `ImageStore` in dev and release alike.** One owner of image files; the interim `FixtureImageFiles` was deleted at integration and probe 30 plants a real `ImageStore` entry. The listing mark is a `listed-by` file beside `image.json`, not a manifest field, because it is this Mac's account state, not part of the image (a copied image must not carry it). Alternative: a manifest field, which would travel with copies.
- **30 — `image.mirror` removes only images the same machine's catalog listed before (`HeldImage.listedBy`), never one with a running operation; others are reported `unknown`.** Signing out removes the machine from the account and a new sign-in is a new machine id, so a plain "delete whatever isn't listed" would erase every image on a re-login; this matches `sandbox.mirror`'s rule. An empty list from a successful subscription does delete, since an account can delete its last image. Alternative: delete anything not listed.
- **30 — `images:forMachine` returns `{ image_id, state }` per holding, and the connector pushes the ids on every change.** Convex only re-sends a query result that changed; with the state included, the `building` → `ready` report re-sends the list after the files exist, so they get marked listed. Alternative: ids only, which would leave a freshly built image unmarked until some other holding changed.
- **30 — The daemon's `image.delete` refuses with `conflict` while an operation on that image runs.** Cancelling a build or copy is the owning slices' (28, 34, 38) call; meanwhile the relay reports that Mac's refusal, and the files go at its next mirror push after the work ends. Alternative: remove the files under the running work.
- **30 — The relay reports a holder's files as removed whenever that Mac answered `image.delete` successfully, whatever `removed` says.** The catalog row goes first, so the Mac's own mirror push can remove the files a moment before the relayed delete arrives; either way they are gone. Alternative: report "nothing to remove" on `removed: false`, which reads wrong in that race.
- **30 — `image.list`'s result rows are exactly the table's facts: `{ name, os, size_bytes, from, on, default }`, `from` and `on` as display strings (`sandbox bold-otter`, `macOS 27.0.1 IPSW`, `release`; `attic (copying)`, `every Mac`).** The slice asks text and JSON to carry the same facts, and every image command takes a name, so ids and timestamps stay in Convex. The text table formats sizes (`4.2 GiB`, `300 MiB`, `-` until known) and marks the default `yes`; its own parity test checks each cell. Alternative: Convex's full rows in JSON, with a table that drops facts.
- **30 — `ActionKind` gains `made_default`; `image default` reports the default it replaced, `image rename` reports both names, and an unchanged name or default is `left_alone`.** Every image command reports what it changed (the map's output standard). Alternative: plain results without an action report.
- **30 — A delete whose image is already gone answers `left_alone`, as `sandbox delete` does.** A replay after the row was dropped can't learn the holders again, and it has nothing left to do. Alternative: `image_not_found`, which would make a lost-answer replay look like a failure.

- **31 — The agent is packaged with `bun build --compile`, pinned to Bun 1.4.4.** One command cross-compiles both targets from a Mac (the linux runtime comes from Bun's cache), the output is byte-identical for the same sources, Bun version and output name, and both binaries run with no runtime installed (linux checked on bare `ubuntu:24.04`). The build refuses any other Bun version, because a different compiler changes every digest. Alternative: a Node single executable application, which keeps Node as the runtime but needs a bundler, `postject`, a pinned linux Node download and separate darwin signing.
- **31 — Bun is a required tool on PATH, not an npm dependency.** npm 11 doesn't run install scripts without approval, and the `bun` package needs its postinstall to place the native binary. `tests/agent-binary.test.ts` skips, saying why, when Bun 1.4.4 is missing (the release-checks CI job has neither Bun nor Docker). Alternative: add `oven-sh/setup-bun` to CI.
- **31 — Standalone executables are built with `--no-compile-autoload-dotenv --no-compile-autoload-bunfig`.** Otherwise the agent loads `.env` and `bunfig.toml` from its working directory (the repo, for the process fixture), and those variables reach every command it runs. Alternative: none that keeps the environment clean.
- **31 — `agent-version.json` is `{ version: "<release>+<12 hex>", sha256: { linux, darwin } }`.** The 12 hex characters are the start of sha256 over `linux:<sha>\ndarwin:<sha>\n`, so a change to either binary is a new version; semver build metadata keeps the release version readable. Digests are bare hex, since the field name already says sha256. Alternative: a separate version per OS.
- **31 — The darwin binary keeps Bun's ad-hoc linker signature; the release doesn't re-sign it.** `codesign --deep` on the app seals `Contents/Resources/guest-agent/` as resources without rewriting those bytes (checked), so the digests in `agent-version.json` stay true. The binary runs inside a macOS guest, not on the host, and slice 33 decides what that guest needs. Alternative: sign it with the release identity before writing `agent-version.json`, inside the build script.
- **31 — The image build builds the agent before hashing its inputs, and hashes only the binary the Dockerfile copies.** Before, `dist/` was hashed before `npm run build`, so a cache hit could be a stale agent. `.dockerignore` now keeps all of `dist/` except `dist/guest-agent` out of the build context. Alternative: keep hashing all of `dist/`.
- **31 — `tests/agent-binary.test.ts` drives the binary over stdin/stdout itself, the way the process fixture does, rather than through the Swift fixture.** The fixture's guest command is Swift (`localbox-hostd/main.swift`), outside this slice. On a Mac the linux binary runs in `docker run --platform linux/arm64 ubuntu:24.04` and the test asserts the container has no Node; the darwin binary runs natively. Alternative: point `ProcessFixtureConfiguration` at the binary (later, with Swift).
- **23 — `SandboxConfigurationBuilder.build` validates; tests inspect the unvalidated `configuration(for:)`.** `validate()` refuses in any process without the virtualization entitlement, and `swift test` runs an unsigned xctest. `VMSpecTests` checks the translation (EFI boot loader, variable store, no kernel), and probe 23 (tier v) proves validation and boot through the signed vmlab. Alternative: sign the xctest bundle in `swift test`, which SwiftPM gives no hook for.
- **23 — the record stores the image id, OS and macOS hardware model, not a boot store path.** The boot store's file name follows from the OS (`SandboxDirectory.bootStore(for:)`: `efi-vars` or `aux.img`), so a stored path would be a second spelling; the hardware model is stored because a restore needs it and the image may be deleted. Alternative: a `boot_store` path field in `sandbox.json`.
- **23 — `os` is set by `provision`, not by `SandboxRecord.init`.** Only the image knows its OS, and the factory is what reads the image (slice 24); `SandboxHost` names only the image id. Alternative: `SandboxHost` reads the manifest first, which would put image file I/O in `SandboxHost`.
- **23 — `VMSpec.devices` is computed from `GuestPlatform.devices(for: os)`, and the translator iterates it.** One list per OS decides what is attached, so "macOS has no entropy device" is a pure assertion. Alternative: device flags on `VMSpec`, which could disagree with the platform.
- **23 — macOS display is 1440x900 at 80 ppi, no window.** Matches the Linux image's desktop size, so desktop operations see one size on both. Alternative: Tart's 1920x1200; slice 35 may revisit with real screenshots.
- **23 — vmlab's `--kernel-args` and the `kernel_command_line` restore sweep are gone.** EFI has no host-side command line, and the direct path is a seam deleted in 24. Alternative: keep them for the seam's lifetime.
- **23 — `AppleVirtualizationBackend(spec:sandboxID:name:)` replaces the lab-only `ConfigurationMaker`.** vmlab builds its experiments as `VMSpec`s (changing the record for the restore sweep), so every lab boot goes through the production translator. Alternative: keep a closure for labs.
- **23 — probe `23-vmspec-bootstore.ts`: tier s runs `VMSpecTests`, tier v boots and hibernates the slice 15 EFI disk through vmlab `--efi`.** The slice names both gates; vmlab is the only real-VM harness before 24 provisions EFI sandboxes in the daemon. Alternative: reuse probe 15, whose evidence file is the spike's record.
- **24 — `cloneForSandbox` returns `ClonedImage { manifest, boot, disk }`, not just the `BootStore`.** Provisioning needs the manifest's OS and hardware model for the record, and the disk's "cloned"/"copied" so a report never claims a thin clone it didn't get. Alternative: the slice's `-> BootStore` plus a second `manifest(id)` read, which could race a `remove`.
- **24 — `image.json` uses snake_case keys (`image_id`, `os`, `size_bytes`, `hardware_model`, `min_macos`, `agent_version`).** Matches `sandbox.json`, the operation journals and the wire contract. Alternative: the slice's camelCase spelling.
- **24 — `size_bytes` is allocated bytes (disk plus boot store), not apparent length.** The linux disk is 8 GiB sparse; what a copy and free-disk placement care about is what it stores. Alternative: apparent size.
- **24 — `commit` uses `renamex_np(RENAME_EXCL)` and `remove` renames to a dot temporary before deleting.** A commit never replaces an image, and a crash mid-delete leaves a temporary `sweepTemps` removes instead of half an image that `list()` would show. Alternative: `moveItem` and `removeItem` directly.
- **24 — `SandboxBackendFactory.provision` is `async`; the actor awaits it, guarded by an in-flight set answering `conflict`.** A nonisolated async call leaves the actor (SE-0338), so a full copy where cloning is unsupported no longer blocks every request; the guard keeps a re-run create from laying down a second copy while the first is still provisioning. Alternative: `Task.detached`, the same hop with more ceremony.
- **24 — `SandboxHost` takes `freeDiskBytes: () -> UInt64?` instead of an `ImageStore`.** The firewall says `SandboxHost` does no image file I/O; capacity only needs a number. Unread free disk is `null`, never 0 (placement reads absent as "not reported"). `macos_version` is `major.minor.patch` from `ProcessInfo`, compared numerically by `atLeast`. Alternative: pass the store.
- **24 — the dev image's `boot/efi-vars` comes from `packages/vm-image/scripts/create-efi-vars.swift`, run with `swift`.** Only Virtualization writes the format; creating one needs no entitlement and fresh stores are byte-identical (checked), so the build needs no signed binary. Alternative: a vmlab subcommand, which ties the image build to building and signing the daemon.
- **24 — `--out` assembles the image from the cached `<profile>-efi` build (APFS clone of `template.img`) rather than building into it.** The build cache and its `manifest.json` stay where they were, and re-running `--out` on a cache hit costs seconds. Alternative: build straight into `<images>/linux`, losing the cache record or putting a build manifest inside the image.
- **24 — proofs build the dev image once at `dist/vm-image/images/linux` (`scripts/proof/lib/linux-image.ts`), and each real daemon's machine root gets an APFS clone of it.** Every probe machine owns its own `images/` the way an installed Mac does, at no cost. Alternative: point `LOCALBOX_IMAGES` at the shared dist directory, where one probe's image op would affect the next.
- **24 — `stack up` does not wipe `images/`.** Sandboxes and operations belong to the wiped Convex account; image files are this Mac's, and the built-in `linux` isn't an account row (P1). Alternative: wipe it with the rest.
- **24 — vmlab takes `--image <images>/<id>` and provisions through `AppleSandboxFactory`; `--artifacts` and `--efi` are gone.** Every lab boot is now the daemon's create path; `efi-kernel` and `efi-clones` keep their names because probe 15's evidence names them. Alternative: keep a template mode for the release's direct artifacts until 25.
- **24 — probes 01, 02, 15 and 23 run vmlab on the dev image; probes 10–13 get it through `realDaemon`.** Adjusted only as far as the image layout needs; slice 25 rewrites 01, 02 and 10 for the shipped image. Alternative: leave them blocked until 25.
- **27 — `freezeAndClone`'s body is async and returns a value (`@Sendable () async throws -> T`).** A synchronous body runs on the runtime actor and blocks it, so status reads, the idle tick and admission would wait on the clone instead of seeing `.freezing` and passing it by; a value lets slice 28 hand back the clone's facts. Alternative: the slice's literal `() throws -> Void`.
- **27 — Self-thaw defaults to 10 s, the guest refuses more than 30 s, and a repeated freeze restarts the timer without freezing twice.** 10 s covers an APFS clone with a wide margin while a dead host's guest is stuck for at most that long. Alternative: 30 s by default.
- **27 — The control lane is dialled once per exclusive operation (retrying for up to 10 s) and every answer has a deadline: 60 s for freeze (its `sync` may flush much), 15 s for thaw.** A connection held for the sandbox's life would need its own reconnect handling after every restore; a deadline keeps a guest that never answers from holding the operation lock. Alternative: one long-lived control connection per boot.
- **27 — Dropping the control connection does not thaw; only the timer does.** A thaw on close would add a second thaw path whose timing depends on the transport; the timer is the one guarantee. Alternative: thaw when the connection that froze closes.
- **27 — A thaw the guest doesn't confirm after a successful body is not an error; it lands in the status detail.** The clone was taken frozen and paused, so it is good, and the guest thaws itself at the timeout. Alternative: fail the clone.
- **27 — The process fixture has no control lane; `freezeAndClone` on it answers `unsupported`.** A fixture guest shares the host's filesystem, so there is nothing to freeze, and its stdin/stdout transport has no second lane. Alternative: a second Unix socket for the fixture with `sync`-only commands.
- **27 — Requests, bring-ups, stops, saves and resizes wait for the operation lock; shutdown includes a `.freezing` sandbox and saves it once it thaws. `.freezing` reports state `running`.** These all touch the lifecycle or the guest, and a clone is short; waiting keeps every lifecycle change ordered after the thaw. A resume that fails after the body leaves the sandbox `.paused`, so its next use resumes it. Alternative: shutdown thaws at once and abandons the clone.
- **27 — Probe 27's "kill the host mid-body" drops the control lane without a thaw on a running guest.** A Virtualization VM dies with the process that runs it, so killing the host can't leave a guest to watch; what the guest sees of a dead host is a control connection that closes with no thaw. Alternative: none on one Mac.
- **32 — The agent's embedded version comes from a first, unversioned build.** The version names a digest of the binaries, and embedding it changes them, so `build-guest-agent.ts` compiles once with an empty version, takes `<release>+<12 hex>` from those digests, then compiles again with it embedded; `sha256` names the shipped (second) binaries. The same sources still give the same version, and any change still changes it. This replaces slice 31's "digest of the shipped binaries". Alternative: a digest of the source bundle, which needs a second bundler pass and misses a Bun runtime change.
- **32 — The ready frame carries `agent_os` beside `agent_version`.** The host must pick which binary to push, and no record field names a sandbox's guest OS until `VMSpec` (slice 23); the agent knows its own platform. Alternative: thread the OS from the backend.
- **32 — The host reads its agent build from `LOCALBOX_GUEST_AGENT`; unset, guests keep the agent their image carries.** Paths reach the daemon explicitly (slice 26). Wiring it into the plist template and `install-release.sh` (`Contents/Resources/guest-agent/`) is release packaging, outside this slice; until then a release does not push. Alternative: derive it from the daemon's own bundle path.
- **32 — `agent-version.json` is re-read whenever its modification time changes, and the check runs on each connect and each idle tick.** A host's build changes only with an install, which restarts the daemon, but re-reading keeps the rule simple (a guest is held to the build on disk now) and lets probe 32 swap builds under a running daemon. Alternative: read once at start.
- **32 — Chunks are 4 MiB raw (about 5.3 MiB as base64), each answered before the next is sent; the last chunk's answer waits up to 60 s, the others 30 s.** One answer per frame keeps the control lane's in-order rule and gives flow control without a window. Alternative: stream every chunk, then one answer.
- **32 — After `updated` the host re-dials the request lane every 200 ms for up to 60 s (socat's own `UNIX-CONNECT` retry) until the agent that answers names the pushed version.** For a moment the old agent still accepts connections: probe 32 saw a re-dial reach it and get closed (the guest was taken for lost) or answered on the old version. systemd restarts the agent at once (`RestartSec=0`), so a minute without the new build is a failure: no answer at all loses the guest; an answer on another version keeps that lane and is reported. Alternative: the guest stops accepting connections before it answers `updated`, which still races across processes.
- **32 — Deferral is checked on both sides: the host asks `guest.activity` under the operation lock, and the guest answers `deferred` if a job started since.** The host's look and the push are not atomic from the guest's side. Alternative: the host check alone.
- **32 — A refused push (sha mismatch, a write error) or an agent that comes back on another version is not pushed again until the next boot.** Retrying every idle tick would resend tens of MiB a second for a fault a retry can't fix. Alternative: exponential backoff.
- **32 — The update action is `agent_updated`, reported with the sandbox's next result; host `system.info` reports `agent_version`.** It is something the host did without a request, like `woke`. Alternative: report it only in the daemon log.
- **32 — P6's darwin TCC rewrite is a named no-op hook (`rewriteDarwinTccGrantsAfterSwap`) run after the swap.** Spike 18 hasn't said whether a replaced binary loses its grants. Alternative: leave no hook and add it in slice 33.
